# Оптимізація відео на сервері

В Admin → Маркетинг → Банери при завантаженні відеофайлу можна ввімкнути «Оптимізувати відео на сервері». Такий самий вибір доступний у швидкому завантаженні в Медіафайлах. Оптимізація початково вимкнена; збереження оригіналу початково ввімкнене. Налаштування не застосовуються до зображень та документів.

Вибір оригіналу:

- Залишити оригінал і нову вебверсію.
- Видалити оригінал після успішного створення та перевірки меншої вебверсії.

Редактор банера очікує завершення фонового завдання і зберігає посилання на оптимізований файл. Якщо оптимізація не вдається, банер не зберігається з неперевіреним результатом, а завантажений оригінал залишається в медіафайлах.

Для вже завантаженого відео оберіть його в Медіафайлах і натисніть «Оптимізувати це відео». Нова версія з’явиться поруч. Якщо оригінал залишено, для наявного банера оберіть новий файл. Якщо оригінал видалено, його старі `/media/...`-посилання автоматично переходять на оптимізований файл без потреби змінювати вже збережені посилання. Фізичний вихідний файл з папки користувача на комп’ютері не змінюється — вибір видалення стосується лише серверної копії.

Підтримуються MP4, WebM, MOV, M4V до 512 МБ і 15 хвилин. Результат — MP4/H.264, ширина до 1280 зі збереженням пропорцій без збільшення, 25 кадрів/с, CRF 24, максимум 2,4 Мбіт/с, AAC для наявного аудіо, faststart. Один процес сервера обробляє чергу послідовно, FFmpeg використовує два потоки. Звук загальних відеофайлів зберігається; банер, як і раніше, відтворюється без звуку.

Статус і результати показуються в блоці «Оптимізація відео» в Медіафайлах. Фонове завдання продовжується при закритті вкладки; завантаження повертає номер завдання, а браузер опитує короткий API. Оригінал не видаляється при помилці FFmpeg/FFprobe, некоректному відео, перевищенні часу обробки або якщо нова версія не менша. Видалення активного вихідного файлу через API медіафайлів заблоковано.

Доступ: `media:write` для завантаження/оптимізації, додатково `media:delete` для вибору видалення оригіналу, `media:read` для історії. Видалення виконується тільки після перевірки H.264, тривалості та розміру, встановлення перенаправлення й перевірки, що оригінал не змінився під час обробки. Метадані копіюються до нової версії.

## Розгортання

Dockerfile встановлює `ffmpeg` (разом із `ffprobe`) у фінальний образ. Потрібно перебудувати образ при розгортанні цієї зміни. Для сервера без Docker встановіть FFmpeg із пакунків ОС; за потреби задайте `FFMPEG_PATH` та `FFPROBE_PATH`. Тимчасові інструменти в `tmp/video-tools` потрібні лише для локальної перевірки й не є залежностями сервера.

Дані завдань, тимчасові результати та таблиця старих посилань зберігаються в `UPLOADS_DIR/.video-optimization`. Ця папка прихована зі списків і недоступна через `/media`. Переносьте весь `UPLOADS_DIR`, включно з прихованою папкою, щоб зберегти старі посилання. Готові відео лежать поряд з оригіналом. Черга призначена для постійного Node.js-процесу (поточне Docker-розгортання), а не serverless-функцій. Після перезапуску перервані завдання через 25 хвилин позначаються як перервані; їх можна запустити повторно. Для кількох серверних процесів потрібен окремий спільний воркер/розподілена черга.

Якщо перед Node.js працює reverse proxy, дозвольте тіла завантажень до 512 МБ (наприклад, `client_max_body_size 512m` у Nginx) та достатній час для самого передавання файлу. Тривале стиснення не утримує HTTP-запит відкритим.

## Перевірки

`npm run typecheck`, `node scripts/check-video-optimization.cjs`, `node scripts/check-banner-playback.cjs`. Інтеграційний тест використовує справжній FFmpeg і тимчасову папку, перевіряє обидва варіанти оригіналу, захист при помилках та більшому результаті, асинхронне завантаження через обидва API, права доступу, редирект і приховування службових файлів. Для тесту задайте `FFMPEG_PATH`/`FFPROBE_PATH`; локально він також може використати інструменти з `tmp/video-tools`.
