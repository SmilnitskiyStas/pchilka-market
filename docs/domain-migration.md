# Перенесення на pchilka-market.ua

## Результат 2026-10-30

Новий Next.js сайт переключено на `https://pchilka-market.ua/` на поточному сервері `5.189.190.36`. DNS не змінювався: основний домен, www та старий піддомен уже вказували на цей сервер. AAAA-записів основного домену та www під час перевірки немає.

`www.pchilka-market.ua` і публічні сторінки `pchilka-new.eatshock.com` перенаправляють на основний домен кодом 308 зі збереженням шляху та query. `/api/`, `/media/`, `/_next/`, `/uploads/` старого піддомену обслуговуються напряму для сумісності зовнішніх POST-клієнтів та відкритих сторінок.

## Сервер

- Next.js: `pchilka-app`, порт хоста `3001`, стан `healthy` після переключення.
- Попередній WordPress: `pchilka-market-app`, порт `3002`; контейнер і БД збережено для відкату.
- nginx: `/etc/nginx/sites-available/pchilka-market.ua` та `/etc/nginx/sites-available/pchilka-new.eatshock.com`. Основний домен проксується на `http://127.0.0.1:3001`.
- WordPress-медіа `/wp-content/uploads/` проксуються на чинний WordPress static backend `127.0.0.1:3002`: прямий alias nginx отримував 403 через права директорій. Перевірений JPG повертає 200. PHP та перегляд директорій у цій location заборонені. До окремого перенесення цих медіа WordPress-контейнер має залишатися запущеним.
- TLS-сертифікат основного домену покриває www та чинний до 2027-01-03.
- Початкове переключення виконано з тим самим образом застосунку, збереженим як `pchilka-domain-migration:20261030-before`.
- Для відтворення використано `/srv/pchilka-app/app/docker-compose.domain.override.yml` з явно заданим образом. Для майбутнього розгортання нового коду цей образ треба оновити.

Інженерна інтеграція до перенесення не мала `/app/.env` чи `ENGINEERING_*` у середовищі контейнера. Її webhook не реєструвався, оскільки чинних налаштувань немає. При налаштуванні використовувати основний домен і постійне сховище `ENGINEERING_ENV_FILE`.

Звернення сервера до власної публічної IP-адреси через HTTPS завершувалося timeout, тоді як зовнішні HTTPS-запити й локальний nginx працювали. Тому внутрішні runner переведені на loopback. Нових cron-завдань не додано; відправлення нагадувань не запускалися як тест.

## Перевірки

- `nginx -t` успішний, виконано reload.
- Публічна головна: 200, Next.js, без старого піддомену в HTML.
- `/api/health/db`: 200, `{"ok":true}`.
- `/robots.txt`, `/sitemap.xml`, `/qr-code/`: 200; sitemap використовує основний домен.
- Перевірені CSS, JS, оптимізоване зображення логотипа і відео `/media/branding/logo/2026/10/1790859443504-1.mp4`: 200.
- Вхід адміністратора й авторизована сесія: 200; cookie має Secure і HttpOnly. Без авторизації `/api/admin/auth/me` повертає 401.
- `getWebhookInfo` трьох ботів: нові адреси, pending=0, помилок немає. Токени, секрети й черги не скидалися.
- Захищені webhook, loyalty ingest, POS ingest, MEGOGO claim на обох доменах без секрету: 401 без редиректу.
- Локальні ключі loyalty і POS перевірено порожнім `{}`: авторизація проходить, очікувані 400 валідації до запису даних. Повне передавання даних не запускалося.
- Перевірено текстові/JSON-поля `site_settings`, `integrations_settings`, `pages`, `public_product_info_display_settings`: старий піддомен не знайдений.
- Внутрішня адреса кожного з трьох runner перевірена через `/api/health/db`: 200.

Повні бізнес-сценарії кас, фактичне отримання нових повідомлень Telegram, відправлення нагадувань і всі зовнішні кабінети окремо не тестувалися. Прямий API старого домену слід зберегти до перевірки всіх зовнішніх клієнтів.

## Резервні копії та відкат

Серверний приватний каталог: `/srv/pchilka-app/backups/domain-20261030-082700`.

Збережено початкові nginx-конфіги, серверний env, compose-файли, Docker inspect та всі рядки `site_settings`. Uploads, бізнес-дані й WordPress не змінювалися. Локальні початкові env і конфіг синхронізації збережено в `%TEMP%/pchilka-domain-migration-local-20261030`. Резервні файли містять секрети, їх не додавати до Git.

Для відкату відновити nginx і серверний `.env.docker` з копії, виконати `nginx -t`, reload і пересоздати лише `app` з образом `pchilka-domain-migration:20261030-before`. Відновити початкові значення трьох Telegram-налаштувань з `site-settings-before.json` і перереєструвати старі webhook. Не перезаписувати всі актуальні `site_settings`, якщо після перенесення були інші зміни. За потреби повернути локальні конфіги з копій. БД WordPress і Next.js не взаємозамінні.

## Додаткове виправлення порожнього списку банерів

Того ж дня за зверненням користувача прибрано запасний `HomeHeroBanner` із `app/page.tsx`. За порожнього списку активних банерів головна більше не показує банер чи індикатор. У робочій таблиці `banners` на момент перевірки 0 записів.

Образ цього етапу: `pchilka-domain-banner:20261030` (`59fbb654627c`), після розгортання стан `healthy`. Змінено source `/srv/pchilka-app/app-git/app/page.tsx` і образ у `docker-compose.domain.override.yml`. Production-збірка й TypeScript успішні; зовнішній HTML підтвердив 0 блоків `home-hero-preview`, `home-banner-carousel`, `home-banner-controls` та наявність основного вмісту. API, CSS/JS і перевірений WordPress JPG повертають 200 після розгортання.

Збірку виконано через приватний `Dockerfile.banner` у каталозі копій: готові `.next` накладено на початковий production-образ. Lock-файли builder і production збігаються; runtime-залежності та налаштування домену збережено. Файл source до зміни: `home-page-before-banner.tsx`; compose до виправлення: `docker-compose.domain.before-banner.yml`; журнал успішної збірки: `banner-targeted-build.log`.

Для відкату лише банера відновити `docker-compose.domain.before-banner.yml` як поточний override і пересоздати тільки `app`, залишаючи новий серверний env і nginx. Це зберігає перенесення домену.

## Окремий доступ до старого WordPress

Архів для перенесення даних: `http://5.189.190.36:3002/`; сторінка піци: `http://5.189.190.36:3002/picza/`.

Після звернення користувача виправлено `WP_HOME` і `WP_SITEURL` у `/srv/pchilka-market/app/pchilka-market.ua/wp-config.php`: вони використовують повну архівну адресу з портом. Раніше WordPress генерував ресурси на основному домені та канонічний редирект із втратою порту.

Встановлено `wp-content/mu-plugins/pchilka-archive-links.php`; копія для перегляду в репозиторії: `deploy/wordpress/pchilka-archive-links.php`. Лише за Host `5.189.190.36:3002` плагін переписує старі абсолютні адреси меню, контенту та JSON-налаштувань frontend на архів. Переписування виконується у відповіді, без заміни даних у БД. Запити основного домену до старих медіа не змінюються.

Перевірки: PHP syntax, головна й `/picza/` повертають 200 без переходу на іншу адресу; посилань меню/ресурсів на основний домен не залишилося; усі 41 унікальні локальні CSS/JS із цих сторінок повертають 200. Основний Next.js health API також 200. Якщо браузер закешував старий 301, відкрити `/picza/?archive=1` або очистити кеш редиректу.

Копія попереднього `wp-config.php`: `/srv/pchilka-app/backups/wordpress-archive-20261030-090512/wp-config.php`. Для відкату цього окремого виправлення відновити config і вимкнути новий MU-плагін. Перенесення Next.js та його БД це не зачіпає.

## Меню власного виробництва та постійні дані піци

Образ етапу виправлення меню: `pchilka-menu:20261030` (`97e81cf4e0cc`), після розгортання стан `healthy`. Піца й інші п'ять native-сторінок `/own-brand/*` враховані як самостійні функціональні сторінки, тому автоматична видимість більше не вимагає для них статей. Явне приховування пунктів залишається дієвим. Довгі desktop-підменю отримали обмеження висоти та вертикальну прокрутку.

Перед перезапуском актуальний `/app/content` скопійовано із зупиненого контейнера, щоб зберегти останні правки користувача. У production Compose додано `/srv/pchilka-app/data/app/content:/app/content`. Файл `own-brand-pizzas.json` після перенесення збігається з копією побайтово; збережена активна піца відображається. Цей volume слід залишати підключеним при наступних розгортаннях і відкатах.

Копії коду, compose, runtime-даних, журнал збірки й сценарій розгортання: `/srv/pchilka-app/backups/menu-20261030-091554`. Для відкату тільки меню повернути image override з `image-before-deploy.yml` і пересоздати лише app, залишаючи content volume. Не відновлювати старий compose без цього volume — він приховає актуальні дані піци.

Зовнішньо перевірено: піца у public menu, всі шість дочірніх сторінок — 200, CSS прокрутки завантажується, health API — 200, запасний банер відсутній. Цільові тести меню, включно з 40 підпунктами, TypeScript і production build успішні. Налаштування меню користувача не перезаписувалися.

## Згорнуті картки піц і вибір магазинів

Поточний образ: `pchilka-pizza-editor:20261030` (`aac46acc78ee`), стан `healthy`. У `/admin/own-brand` збережені картки спочатку згорнуті, нові відкриваються для введення. Додано окремий вибір магазинів із пошуком і публікацією через `GET/PUT /api/admin/own-brand/pizza-stores`. Схему та дані таблиці stores не змінювали; вибір зберігається як ID в `UPLOADS_DIR/own-brand/pizza-stores.json`.

Під час перевірки редактор завантажив 19 піц і 36 доступних магазинів; початковий вибір магазинів не публікувався автоматично. Піци після перезапуску збережено побайтово. Інструкція: `docs/own-brand-pizza-editor.md`.

На момент цього розгортання у контейнері вже існував `/app/.env` із чинними налаштуваннями інженерної служби, створеними після початкового перенесення домену. Актуальний файл скопійовано зі зупиненого контейнера без зміни вмісту в `/srv/pchilka-app/data/app/engineering/.env`; активний Compose отримав bind mount `/app/data/engineering` та `ENGINEERING_ENV_FILE=/app/data/engineering/.env`, які вже передбачені актуальним файлом Compose репозиторію. Файл і каталог приватні, значення секретів не виводилися; повторної реєстрації webhook не виконувалося.

Копії source, runtime-даних, старого image override та compose, журнал збірки й сценарій розгортання: `/srv/pchilka-app/backups/pizza-editor-20261030-101404`. Для відкату коду повернути image override з `image-before-deploy.yml`, залишаючи всі три постійні mounts: uploads, content та engineering. Не перезаписувати актуальні налаштування й дані копіями без окремої потреби відновлення.

Перевірки: цільовий тест `scripts/check-own-brand-editor.cjs`, TypeScript, production build; авторизований GET нового API — 200, анонімний — 401; сторінки редактора та піци — 200; всі 11 ресурсів редактора — 200; меню й DB health працюють. Тести збереження вибору та публічного показу виконані ізольовано, без зміни магазинів на production.
