# Інженерний Help Desk

Розділ адміністратора: `/admin/engineering` → «Мережа та звернення» → «Інженерний Help Desk». Доступ до API налаштувань, користувачів та історії має лише системний адміністратор.

## Підключення

1. У розділі вказати `engineer@legion2015.com`, пароль, IMAP-сервер, TLS-порт (типово 993) та папку `INBOX`. Адресу IMAP-сервера потрібно отримати від адміністратора пошти; вона не вгадується за доменом.
2. Вказати токен саме `@engineering_dep_pchilka_bot` із BotFather та публічну HTTPS-адресу сайту без шляху.
3. Натиснути «Підключити Telegram»: поточні поля форми спочатку збережуться. Перед реєстрацією webhook перевіряється username бота через `getMe`; після неї перевіряється адреса через `getWebhookInfo`. Кнопка «Перевірити Telegram» показує відповідність адреси сайту, кількість оновлень у черзі та останню помилку доставки з датою.
4. У блоці працівників вказати ім’я та натиснути «Створити запрошення». Перед видачею посилання сайт автоматично зберігає налаштування й реєструє webhook із поточним секретом. Якщо токен, HTTPS-адреса або реєстрація некоректні, посилання не створюється. Скопіювати персональне посилання й передати працівнику. Telegram ID вводити не потрібно: бот визначить його сам після відкриття посилання та натискання «Почати». Реєстрація працівників і команди працюють незалежно від перемикача автоматичної перевірки пошти. Команда `/id` залишається лише допоміжним засобом визначення ID спільного чату.
5. За потреби вказати окремий ID групи або `@назву_каналу`. Бот має мати право надсилати туди повідомлення; у каналі — бути адміністратором. Username бота не є каналом призначення. При заповненому каналі повідомлення надсилаються і в канал, і працівникам.
6. Увімкнути «Автоматично перевіряти пошту й надсилати нові запити», зберегти та натиснути «Перевірити пошту зараз». Початковий імпорт обмежено останніми 7 днями; далі читаються нові UID. Прочитані листи також імпортуються; прапорці листів не змінюються. Якщо перевірка пошти вимкнена, бот усе одно відповідає на /start, активує запрошення та дозволяє працювати з уже збереженими завданнями.

Якщо після «Почати» немає відповіді, натисніть «Перевірити Telegram». Невідповідна адреса webhook потребує повторного «Підключити Telegram»; остання помилка доставки Telegram допоможе відрізнити HTTP 401 (секрет webhook), 404 (маршрут або розгортання), 500 (помилка застосунку/БД) та проблеми HTTPS. Повторне підключення оновлює секрет і не очищає чергу Telegram. Після виправлення відкрийте персональне посилання знову та натисніть «Почати». Зареєстрована адреса підтверджує конфігурацію, але не гарантує успішну доставку: остання помилка може описувати попередню спробу, тому враховуйте її дату.

## Зберігання і запуск

Пароль, токен, логін та інші параметри зберігаються у файлі `.env`, типово в корені проєкту, а не в MySQL. Шлях можна задати **на сервері** через `ENGINEERING_ENV_FILE`; клієнт не може його змінити. Адмінпанель показує цільовий файл і фактичне джерело завантажених налаштувань. Якщо при переході на новий шлях файл ще не створено, попередній кореневий `.env` читається як джерело для перенесення; наступне збереження записує інженерні параметри до нового файлу. Наявний файл за ENGINEERING_ENV_FILE має пріоритет над кореневим і змінними процесу.

Значення записуються як JSON-рядки, щоб коректно зберегти пробіли, лапки, `#` та зворотні слеші. Читання налаштувань і планувальник використовують один парсер: також підтримуються старі записи з пробілами навколо `=`, `export`, одинарними лапками та значення прапорця `1`, `true`, `yes`, `on`. Сторонні змінні `.env` зберігаються. Після запису файл повторно читається й усі значення порівнюються із запитаними. Помилка запису/доступу відображається явно, без повідомлення про успіх.

У полях пароля та токена показується маска `••••` з останніми чотирма символами збереженого значення. Повні пароль і токен, секрет webhook та ключ запуску не повертаються в GET/PUT. Порожні поля пароля й токена залишають попередні значення. IMAP-сервер і публічна HTTPS-адреса відображаються повністю. Галочка застосовується після «Зберегти»; незбережені зміни позначаються у формі. Значення після успішного запису беруться з підтвердженої відповіді сервера, а оновлення списку завдань їх не перезаписує.

Завантаження форми (`GET /api/admin/engineering?section=settings`) не потребує підключення до БД. Помилка завантаження завдань або працівників показується окремо та не блокує збереження `.env`. Налаштування читаються під час кожної операції, тому перезапуск після збереження не потрібний.

`npm start` через `start-next.cjs` запускає перевірку раз на 30 секунд внутрішнім HTTP-запитом до `/api/engineering/run`, захищеним `x-engineering-secret`. Прямий `next start` і `npm run dev` цього планувальника не запускають: доступна ручна перевірка з адмінпанелі або окремий захищений виклик run API. Перша автоматична перевірка відбувається через 30 секунд після запуску. Для нестандартного порту задайте `PORT` у середовищі.

У production Docker додано постійний каталог `/srv/pchilka-app/data/app/engineering` → `/app/data/engineering`, а `ENGINEERING_ENV_FILE=/app/data/engineering/.env`. Секрети переживають перевипуск контейнера, коли ці зміни Compose застосовані на сервері. Без підключеного постійного каталогу файл усередині контейнера може втратитися під час його заміни. Каталог має бути доступний для запису процесу застосунку. Не розміщуйте `.env` у public/uploads. `.env` і `.env.*` виключені з Docker-контексту та Git. На Unix тимчасовий файл створюється з правами 0600; на Windows доступ визначає ACL каталогу.

Сім таблиць `engineering_*` створюються при першому зверненні. Для БД без прав CREATE застосувати `docs/sql/043_create_engineering_help_desk.sql` та `docs/sql/044_create_engineering_invites.sql` перед запуском. Для вже підключеного Help Desk потрібна лише додаткова міграція 044. Дані та історія відокремлені від ботів вакансій, інвентарю й тестового бота.

## Запити та доступ

Персональне посилання має вигляд `https://t.me/engineering_dep_pchilka_bot?start=eng_<випадковий_токен>`. Воно діє 7 днів і призначене для одного працівника. У БД зберігається лише SHA-256 токена; посилання повертається лише при створенні та не доступне у списку запрошень. Після оновлення сторінки створіть нове посилання за потреби, скасувавши попереднє невикористане. Адмінпанель показує статуси очікування, активації, скасування та завершення строку дії.

Запрошення приймається лише в особистому чаті з ботом. Перший користувач, який активує посилання, отримує ім’я, задане адміністратором, і доступ до завдань та особистих сповіщень. Токен і доступ записуються однією транзакцією з блокуванням запрошення. Інший Telegram-акаунт не може використати це посилання повторно. Повторна доставка того самого /start для вже прив’язаного активного користувача безпечна; після видалення доступу старе посилання його не відновить. Для відновлення адміністратор створює нове запрошення. Чинні працівники, додані раніше за ID, зберігають доступ.

Посилання передається саме потрібному працівнику: до активації воно надає доступ тому, хто його відкриє. Скасування невикористаного запрошення не впливає на інших працівників. Видалення активного працівника також скасовує його запрошення та невикористані запрошення з тим самим іменем; для різних працівників використовуйте повні імена.

Відбираються листи з точною адресою `From: legion_admin@legion2015.com`, MIME-тема й текст декодуються. Ідентифікатор розпізнається з позначок `Tracking ID`, `Ticket ID`, «Ідентифікатор відстеження», «Номер запиту», «Номер заявки» або номера в темі. Листи з однаковим ідентифікатором оновлюють одне завдання, зберігаючи попередні листи та відповідального. Без номера використовується стабільний `MAIL-…` на основі Message-ID (або UID). Повторна перевірка не створює дубль листа. Реальний зразок Help Desk може потребувати розширення правил розпізнавання.

У Telegram доступні списки «Усі», «Нові», «Мої», перегляд тексту та історії, «Взяти в роботу», «Повернути в чергу» й «Завершити». Захоплення завдання та журнал дій записуються однією транзакцією з блокуванням рядка. Повернути або завершити може лише поточний відповідальний. Адміністратор може повернути активне завдання в чергу на сайті, зокрема після видалення працівника; це також потрапляє в журнал.

Видалення користувача вимикає його доступ до даних і наступних відправлень та зберігає авторство попередніх дій. Воно не видаляє вже отримані повідомлення й не змінює членство людини в Telegram-каналі/групі — це керується в самому Telegram. Читання завдань у боті дозволене лише активним користувачам в особистому чаті або налаштованому спільному чаті.

## Доставка та межі

Одержувачі фіксуються на момент імпорту листа. Новий працівник бачить попередні запити через список, але не отримує розсилку всієї історії. Надсилання й повторні спроби зберігаються в БД для кожного адресата та частини листа; помилка одного адресата не зупиняє інших. Черга не має строку давності. Збій IMAP не зупиняє відправлення вже збереженої черги. Статуси раніше розісланих карток оновлюються після дій, наскільки це дозволяє Telegram; джерело актуального стану — БД і новий перегляд завдання.

За одну перевірку імпортується до 50 листів і обробляється до 200 частин повідомлень. Текст понад 2600 символів розбивається на додаткові повідомлення по 3800 символів. Вкладення не пересилаються. Лист понад 20 МБ зупиняє просування курсора до ручного опрацювання; максимальний збережений текст — 250 000 символів. Можливий повтор повідомлення при невизначеному результаті мережевого запиту Telegram або аварії між прийманням Telegram і записом message_id у БД; Bot API не надає ключа ідемпотентності sendMessage.

Перевірки: `node --test scripts/check-engineering.cjs`, `npm run typecheck`, `npm run build`. Перевірка реальної пошти й доставки потребує введених адміністратором пароля, IMAP-сервера, токена та реєстрації webhook.

Документація інтеграцій: [ImapFlow](https://imapflow.com/docs/api/imapflow-client/), [MailParser](https://nodemailer.com/extras/mailparser), [Telegram Bot API](https://core.telegram.org/bots/api), [Telegram deep links](https://core.telegram.org/bots/features#deep-linking).
