# Інженерний Help Desk

Розділ адміністратора: `/admin/engineering` → «Мережа та звернення» → «Інженерний Help Desk». Доступ до API налаштувань, користувачів та історії має лише системний адміністратор.

## Підключення

1. У розділі вказати `engineer@legion2015.com`, пароль, IMAP-сервер, TLS-порт (типово 993) та папку `INBOX`. Адресу IMAP-сервера потрібно отримати від адміністратора пошти; вона не вгадується за доменом.
2. Вказати токен саме `@engineering_dep_pchilka_bot` із BotFather та публічну HTTPS-адресу сайту без шляху.
3. Зберегти налаштування та натиснути «Підключити Telegram». Перед реєстрацією webhook перевіряється username бота через `getMe`.
4. Додати працівників за числовими Telegram ID та іменами. Команда `/id` у боті доступна без дозволу та повертає лише ID користувача і чату. Кожен працівник має надіслати боту `/start`; лише після цього він отримуватиме особисті сповіщення.
5. За потреби вказати окремий ID групи або `@назву_каналу`. Бот має мати право надсилати туди повідомлення; у каналі — бути адміністратором. Username бота не є каналом призначення. При заповненому каналі повідомлення надсилаються і в канал, і працівникам.
6. Увімкнути модуль, зберегти та натиснути «Перевірити пошту зараз». Початковий імпорт обмежено останніми 7 днями; далі читаються нові UID. Прочитані листи також імпортуються; прапорці листів не змінюються.

## Зберігання і запуск

Пароль, токен, логін та інші параметри зберігаються в `.env`, типово в корені проєкту. Шлях можна задати **на сервері** через `ENGINEERING_ENV_FILE`; клієнт не може його змінити. Значення записуються як JSON-рядки, щоб коректно зберегти пробіли, лапки, `#` та зворотні слеші. Сторонні змінні `.env` зберігаються. Порожній пароль/токен у формі залишає попереднє значення. Секрети не повертаються в GET/PUT; секрет webhook і ключ запуску генеруються автоматично. Файл читається під час кожної операції, тому перезапуск після збереження не потрібний.

`npm start` через `start-next.cjs` запускає перевірку раз на 30 секунд внутрішнім HTTP-запитом до `/api/engineering/run`, захищеним `x-engineering-secret`. Прямий `next start` і `npm run dev` цього планувальника не запускають: доступна ручна перевірка з адмінпанелі або окремий захищений виклик run API. Перша автоматична перевірка відбувається через 30 секунд після запуску. Для нестандартного порту задайте `PORT` у середовищі.

У production Docker додано постійний каталог `/srv/pchilka-app/data/app/engineering` → `/app/data/engineering`, а `ENGINEERING_ENV_FILE=/app/data/engineering/.env`. Секрети переживають перевипуск контейнера. Каталог має бути доступний для запису процесу застосунку. Не розміщуйте `.env` у public/uploads. `.env` і `.env.*` виключені з Docker-контексту та Git. На Unix тимчасовий файл створюється з правами 0600; на Windows доступ визначає ACL каталогу.

Шість таблиць `engineering_*` створюються при першому зверненні. Для БД без прав CREATE застосувати `docs/sql/043_create_engineering_help_desk.sql` перед запуском. Дані та історія відокремлені від ботів вакансій, інвентарю й тестового бота.

## Запити та доступ

Відбираються листи з точною адресою `From: legion_admin@legion2015.com`, MIME-тема й текст декодуються. Ідентифікатор розпізнається з позначок `Tracking ID`, `Ticket ID`, «Ідентифікатор відстеження», «Номер запиту», «Номер заявки» або номера в темі. Листи з однаковим ідентифікатором оновлюють одне завдання, зберігаючи попередні листи та відповідального. Без номера використовується стабільний `MAIL-…` на основі Message-ID (або UID). Повторна перевірка не створює дубль листа. Реальний зразок Help Desk може потребувати розширення правил розпізнавання.

У Telegram доступні списки «Усі», «Нові», «Мої», перегляд тексту та історії, «Взяти в роботу», «Повернути в чергу» й «Завершити». Захоплення завдання та журнал дій записуються однією транзакцією з блокуванням рядка. Повернути або завершити може лише поточний відповідальний. Адміністратор може повернути активне завдання в чергу на сайті, зокрема після видалення працівника; це також потрапляє в журнал.

Видалення користувача вимикає його доступ до даних і наступних відправлень та зберігає авторство попередніх дій. Воно не видаляє вже отримані повідомлення й не змінює членство людини в Telegram-каналі/групі — це керується в самому Telegram. Читання завдань у боті дозволене лише активним користувачам в особистому чаті або налаштованому спільному чаті.

## Доставка та межі

Одержувачі фіксуються на момент імпорту листа. Новий працівник бачить попередні запити через список, але не отримує розсилку всієї історії. Надсилання й повторні спроби зберігаються в БД для кожного адресата та частини листа; помилка одного адресата не зупиняє інших. Черга не має строку давності. Збій IMAP не зупиняє відправлення вже збереженої черги. Статуси раніше розісланих карток оновлюються після дій, наскільки це дозволяє Telegram; джерело актуального стану — БД і новий перегляд завдання.

За одну перевірку імпортується до 50 листів і обробляється до 200 частин повідомлень. Текст понад 2600 символів розбивається на додаткові повідомлення по 3800 символів. Вкладення не пересилаються. Лист понад 20 МБ зупиняє просування курсора до ручного опрацювання; максимальний збережений текст — 250 000 символів. Можливий повтор повідомлення при невизначеному результаті мережевого запиту Telegram або аварії між прийманням Telegram і записом message_id у БД; Bot API не надає ключа ідемпотентності sendMessage.

Перевірки: `node --test scripts/check-engineering.cjs`, `npm run typecheck`, `npm run build`. Перевірка реальної пошти й доставки потребує введених адміністратором пароля, IMAP-сервера, токена та реєстрації webhook.

Документація інтеграцій: [ImapFlow](https://imapflow.com/docs/api/imapflow-client/), [MailParser](https://nodemailer.com/extras/mailparser), [Telegram Bot API](https://core.telegram.org/bots/api).
