# Статті на сторінках меню

В Admin → Контент (`/admin/content`) є один вибір «Де опублікувати матеріал»:

- **Окрема стаття:** Блог, Новини мережі або Благодійність. Матеріал отримує окрему адресу і картку розділу; заголовок, короткий опис, обкладинка та основний текст обов’язкові. Категорії належать обраному розділу.
- **Текст на сторінці сайту:** конкретна сторінка меню. Матеріал відображається повністю на сторінці; назва текстового блоку для адмінпанелі й текст обов’язкові, короткий опис та обкладинка — необов’язкові. Назва не виводиться автоматичним заголовком на сайті, щоб не дублювати заголовок готової сторінки. Якщо потрібен підзаголовок у самому тексті, додайте його через H2/H3 у редакторі. Категорії для такого тексту не використовуються.

Поле «Розміщення тексту» дозволяє вибрати початок або кінець сторінки. Для п’яти сторінок співпраці додатково доступне «Над формою» — це початкове значення при виборі цих сторінок. Текст над формою завантажується на сервері безпосередньо в основний вміст перед формою; він не дублюється в загальному блоці layout. На сторінці «Запропонувати товар» текст залишається видимим, навіть якщо форму вимкнено в її налаштуваннях.

**Приклад для оренди:** оберіть «Пропонуємо в оренду — /cooperation/rental», розміщення «Над формою», введіть назву блоку й текст, встановіть «Опубліковано» й натисніть «Додати матеріал». Статус «Чернетка» зберігає матеріал тільки для адміністраторів. Для існуючого тексту відкрийте його у списку й натисніть «Редагувати».

Посилання веде до матеріалу на обраній сторінці або до окремої статті. Неопубліковані матеріали за публічним посиланням не відображаються. Якщо сервер відхилив збереження, редактор зберігає введені дані та показує помилку.

Призначення зберігається як необов’язкове поле `pagePath`, розміщення — `placement` (`before-content`, `before-form`, `after-content`) у наявних даних `blog_content_v1` таблиці `site_settings`; зміна схеми БД не потрібна. Старі записи без `pagePath` залишаються у своїх розділах. Відсутнє `placement` означає `after-content`, тому існуючі тексти залишаються на попередньому місці до явного редагування. Статті з іншим призначенням не дублюються у блозі, новинах або благодійності. Сервер перевіряє допустимі сторінки та розміщення; «Над формою» недоступне для інших сторінок.

Сторінка «Чому Пчілка не Бджілка» показує призначені опубліковані статті безпосередньо в основному вмісті з серверним завантаженням. Якщо статей немає, використовується наявний старий текстовий файл; відсутність цього файлу не показує відвідувачам технічного повідомлення. Спільний блок статей у layout пропускає цю сторінку, щоб не дублювати матеріали.

Сторінка `/loyalty/rules` також показує призначені опубліковані тексти безпосередньо у власному основному вмісті. Заголовок і правила перебувають в одній картці: PageArticles використовує варіант inline без власних рамки, фону, тіні й додаткових внутрішніх відступів. Якщо такі тексти є, `program_rules.txt` не читається, а спільний блок layout не дублює правила. Старі значення розміщення, зокрема `before-content` та `after-content`, залишаються допустимими при збереженні; правила завжди показуються одразу під h1, а не після min-h-screen основної сторінки. Файл використовується лише за відсутності опублікованого тексту з адмінпанелі та також показується в цій самій картці. Якщо немає обох джерел, показується звичайне повідомлення про неопубліковані правила без технічного шляху. Перевірка: `node scripts/check-loyalty-rules.cjs`.

Головне меню на комп’ютері та в мобільній версії приховує інформаційні сторінки без опублікованих статей. Чернетки не вважаються наповненням. Наявні статичні статті блогу, новин і благодійності також враховуються. Порожні групи меню приховуються. Функціональні сторінки (головна, каталог, шок ціна, магазини, контакти, звітність, кар’єра, застосунок, форми співпраці) доступні незалежно від статей. Прямі адреси прихованих сторінок залишаються доступними.

Публічний `/api/site/content` віддає тільки опубліковані призначені статті та список наповнених сторінок. Навігація і статті використовують дані в пам’яті поточної вкладки протягом 30 секунд, щоб швидкі переходи не повторювали однакові запити. Після цього наступний перехід завантажує актуальні дані. Повернення фокусу примусово оновлює їх, а відвідування адмінпанелі очищає кеш. Одночасні запити поділяють одне завантаження; помилки не кешуються. Так само повторно використовується публічний список SEO-правил. Приватні дані й відповіді адміністративних дій не кешуються. Публічне читання `/api/admin/blog/content` також виключає чернетки; авторизовані адміністратори бачать усі записи.

Загальний `app/loading.tsx` показує стан переходу та дозволяє Next.js попередньо завантажувати оболонку динамічних сторінок. Шапка й меню залишаються інтерактивними під час завантаження наступної сторінки.

Сторінки окремих публікацій `/news/[slug]`, `/blog/[slug]` та `/about/charity/[slug]` використовують динамічний режим Next.js. Вони мають відкриватися для slug, створених після збірки. Порожні списки статичних матеріалів не використовуються для `generateStaticParams`: це спричиняло HTTP 500 `Page changed from static to dynamic at runtime` при читанні актуальних налаштувань сайту. Після `npm run build` запустіть `node node_modules/next/dist/bin/next start --hostname 127.0.0.1 --port 3197` та виконайте `node scripts/check-public-post-routes.cjs` для перевірки нових адрес без записів у БД.

Перевірки: `npm run typecheck`, `node scripts/check-menu-content.cjs`. Інтеграційний сценарій підміняє тільки репозиторій БД у процесі тесту й не змінює робочий контент.
