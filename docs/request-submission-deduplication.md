# Повторні відправлення форм співпраці

Під час перевірки inbox знайдено 21 запис №18–38 з однаковими контактами, компанією, текстом та PDF. На кожен запис є окремий успішний POST `/api/requests` і завантаження файлу. Контрольні суми PDF збігаються; відрізняються ID, час, URL та технічний lastModified вкладення. Опитування `/admin/messages` замінює список і не створює записів.

## Захист у формах

Усі чотири компоненти форм співпраці використовують `useRequestSubmission`:

- синхронний ref блокує повторне натискання ще до першого await завантаження;
- поля та кнопка заблоковані до завершення обробки, кнопка показує «Надсилання...»;
- помилка завантаження також обробляється й повертає форму в доступний стан;
- повтор після помилки використовує вже завантажений файл і той самий Idempotency-Key для незмінного тіла;
- зміна даних або успішне завершення починає нове логічне відправлення з іншим ключем.

Це не заборона на навмисне нове звернення з тим самим текстом. Фільтруються повтори конкретного відправлення, а не всі подібні заявки.

## API та зберігання

`POST /api/requests` приймає необов'язковий `Idempotency-Key`: 16–128 символів `a-z`, `A-Z`, `0-9`, `_`, `-`. Без ключа зберігається сумісність наявних клієнтів і Telegram-бота.

За ключем у межах типу заявки протягом 24 годин повертається попередній запис. Тіло порівнюється за SHA-256 нормалізованих полів із детермінованим порядком ключів JSON. Інше тіло з тим самим ключем повертає 409; очікування зайнятого блокування — 503 з Retry-After. Некоректний ключ — 400.

Хеш ключа та відбиток містяться в службових полях `metadata_json`; вони приховані у відповідях через mapper. INSERT заявки та receipt є одним записом, тому помилка читання чи втрачена відповідь після INSERT не потребують нового рядка при повторі. Схема БД не змінюється.

Конкурентні повтори серіалізуються MySQL GET_LOCK на одній виділеній connection. Усі запити INSERT/SELECT виконуються на тій самій connection, блокування звільняється до повернення connection у pool. При помилці звільнення connection знищується. Це розраховано на поточний один MySQL writer; семантика й обмеження описані в [документації MySQL 8.4](https://dev.mysql.com/doc/refman/8.4/en/locking-functions.html).

## Погоджене очищення

Користувач явно підтвердив видалення №19–38 зі збереженням №18. Перед DELETE перевірено відповідність усіх рядків резервній копії, статусів та PDF. Видалено рівно 20 рядків однією транзакцією; №18 і його вкладення залишилися. Файли вкладень не видалялися.

Приватна копія: `/srv/pchilka-app/backups/messages-20261030-110011/requests-18-38-before.json`. Вона містить персональні дані та не входить до репозиторію. Нові бізнес-заявки для тестів не створювалися.

## Перевірки та стан

`node scripts/check-request-submissions.cjs` перевіряє 20 конкурентних повторів, конфлікт тіла, втрату відповіді після запису, timeout/cleanup блокування, строк receipt і поведінку всіх форм під час upload/POST. `node scripts/check-career-applications.cjs` перевіряє сумісність вакансій і бота. TypeScript проходить.

На робочій БД окремо перевірено синтаксис receipt lookup та поведінку двох connection з GET_LOCK без створення заявок. За вказівкою користувача код підготовлено для коміту без серверної збірки чи розгортання; захист почне діяти після наступного розгортання цього коду.
