# Перевірка затримок переходів між сторінками

Виконано публічні HTTP-запити до https://pchilka-new.eatshock.com без авторизації та записів даних. Для головної, новин, контактів, історії назви й мобільного застосунку отримано одразу HTTP 200 без Location. Ланцюжків переадресацій на цих адресах не виявлено. `/news/` має один очікуваний 308 на `/news`, `/loyalty/about` — один 308 на актуальну `/loyalty/mobile-app`. Посилання поточного меню ведуть на актуальні адреси.

Орієнтовні виміри з поточного комп’ютера в одній сесії (не норматив для всіх відвідувачів):

| Запит | Час до заголовків | Повний запит |
| --- | ---: | ---: |
| Перше відкриття головної | 2325 мс | 2616 мс |
| /news | 327 мс | 328 мс |
| /about/contacts | 373 мс | 374 мс |
| /about/why-pchilka-not-bdzhilka | 702 мс | 703 мс |
| /loyalty/mobile-app | 1053 мс | 1054 мс |

Подальші RSC-запити, які використовуються навігацією Next.js: новини 106–316 мс, контакти 162–450 мс, застосунок 179–244 мс. Публічні API меню/контенту — близько 216–258 мс, SEO — 63 мс. Відповіді меню й контенту невеликі (приблизно 2–3 КБ). Ці заміри відділяють переадресації від часу очікування відповіді, але не вимірюють повний браузерний час малювання/зображень.

Користувач уточнив повільний перехід: `/loyalty/mobile-app` → `/news`, і повідомив, що на момент уточнення затримка вже зникла. Постійне уповільнення цього переходу не відтворене; точна причина одноразової затримки не підтверджена. Повторні запити й відсутність стану очікування є знайденими можливостями покращення, а не доведеною причиною того конкретного випадку.

Знайдено повторне завантаження однакових меню, контенту й SEO при кожній зміні pathname та відсутність loading boundary. Додано кеш у пам’яті вкладки на 30 секунд тільки для трьох публічних наборів даних, спільні незавершені запити, примусове оновлення при focus та очищення при вході в адмінпанель. Зміна маршруту більше не скасовує загальний запит, який потрібний наступній сторінці. SEO-відповідь старого переходу не застосовується після cleanup, а відмови обробляються без необроблених promise rejection. Приватні адміністративні відповіді не кешуються.

Додано легкий доступний стан завантаження app/loading.tsx для швидкої реакції динамічної навігації й попереднього завантаження оболонки. Зменшення фактичного часу переходів на production після цих змін ще не заміряне, оскільки зміни не розгорнуті.

Перевірки: п’ять сценаріїв scripts/check-public-site-cache.cjs пройшли (повторне використання/TTL, спільний запит між переходами, force refresh, повтор після помилки, очищення з незавершеним старим запитом); TypeScript успішний. `/news/vse-bude-dobre` на production ще повертає 500; попереднє виправлення static-to-dynamic залишається в робочих змінах і потребує розгортання разом із цією задачею.

Production build пройшов. Після додавання loading boundary чотири локальні HTTP-перевірки публікацій через scripts/check-public-post-routes.cjs також повернули 200; git diff --check успішний. Тимчасовий сервер зупинено. Коміт і розгортання не виконувалися.

Довідка Next.js: https://nextjs.org/docs/15/app/getting-started/linking-and-navigating та https://nextjs.org/docs/15/app/api-reference/file-conventions/loading.
