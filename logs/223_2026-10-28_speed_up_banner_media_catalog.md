# Прискорення каталогу медіа для банерів

На `/admin/home-slides` ефект завантаження каталогу залежав від `isMediaLoading`. Установлення цього стану в true запускало cleanup поточного ефекту, після чого результат власного запиту ігнорувався, а індикатор міг залишатися активним. Також каталог монтував усі оригінали зображень і відео з preload metadata одночасно.

Зміни:

- Завантаження винесено в useMediaCatalog: стабільні залежності, AbortController при закритті, ізоляція застарілих відповідей, кеш списку на 30 секунд, явне оновлення та повтор після помилки. Порожній каталог теж кешується.
- Показ по 24 файли з переходом між сторінками; пошук працює по всьому списку, зміна фільтра повертає на першу сторінку.
- Зображення показуються через Next Image зі зменшеними розмірами, quality 60 та lazy loading. URL з пробілами, кирилицею й існуючим percent encoding обробляються коректно. Вибір зберігає оригінальне посилання, а не URL прев’ю.
- Для відео використовується легка позначка замість автоматичного запиту метаданих. Помилка прев’ю більше не запускає повторне скачування оригінального файла для діагностики.
- API зберігання банерів і медіафайлів та оригінальні файли не змінені.

Перевірки: `node scripts/check-media-catalog.cjs` (повторні render, закриття й повторне відкриття, запізнілі відповіді, кеш, помилки, оновлення, пагінація, кодування шляхів); повна `npm run build` — exit 0, 203 статичні сторінки. У браузері перевірено production-процес Next start: створення банера → каталог, завершене завантаження оптимізованого прев’ю `/_next/image?...&w=384&q=60`, повторне відкриття та підстановку оригінального шляху після вибору. Для локального процесу використано тимчасовий обліковий запис через змінні середовища; конфігурація облікових записів і робоча БД не змінювались. Банер не зберігався. Знімок: `outputs/banner-catalog-fast.jpg`.

Коміт і розгортання не виконувалися.
