# Перевірка повторних заявок і захист від повторного відправлення

Підтверджено 21 окремий запис №18–38: контакти, текст, компанія та PDF однакові, є 21 успішне POST-відправлення форми обладнання. Відмінності вкладень — адреси завантаження та lastModified, контрольна сума вмісту одна. Polling адмінки не створює нових рядків.

За явним підтвердженням користувача видалено №19–38 однією транзакцією після повторної перевірки незмінності записів та вкладень. №18 і його PDF збережено. Приватна копія всіх 21 запису: `/srv/pchilka-app/backups/messages-20261030-110011/requests-18-38-before.json`. Вкладення залишені на диску.

Додано спільний client hook для всіх форм співпраці: синхронне блокування перед upload, disabled/busy стан, finally для відновлення після помилки, кеш upload та Idempotency-Key при повторі незмінного запиту. API зберігає receipt у службових JSON-полях, порівнює fingerprint, серіалізує конкурентні запити через одну connection і повертає наявну заявку замість повторного INSERT. Службові поля приховані з API; сумісність клієнтів без ключа збережена. Міграція схеми не потрібна.

Перевірки пройшли: `scripts/check-request-submissions.cjs`, `scripts/check-career-applications.cjs`, `tsc --noEmit --incremental false`, `git diff --check`. Ізольовані тести не створюють робочих заявок і не надсилають повідомлень. На сервері додатково перевірені lookup SQL та named lock без записів.

Користувач попросив тільки коміт, без серверної збірки. Новий код на сервер не передавався й не розгортався. Очищення БД було окремо погоджене й виконане. Деталі: `docs/request-submission-deduplication.md`.
